## Context

The project has already established three governed Raspberry Pi target slices:

- native sync/build and target-side integration launch from the governed workspace
- correct target version metadata without syncing `.git`
- installable bundles that populate `$OBC_HOME/obc-deploy/current`

Those slices stop just short of a governed boot/startup path. The installed release still launches through an interactive helper, and the OBC runtime currently assumes it may receive REPL commands on stdin. A real target autostart path needs a service manager, a headless runtime mode, and reviewable evidence that the installed `current` release comes back after reboot.

The Raspberry Pi target is running `systemd 252`, and the account can use `sudo -n`, so the first autostart slice can integrate with a system-level service instead of depending on a lingering user service.

## Goals / Non-Goals

**Goals:**

- provide a governed systemd-managed startup path for the installed Raspberry Pi release
- keep the installed release rooted at `$OBC_HOME/obc-deploy/current`
- allow the OBC runtime to run headlessly under systemd without exiting because stdin is closed
- provide repo-local helper scripts to install, inspect, and probe the service
- capture reviewable post-reboot evidence from real target hardware

**Non-Goals:**

- implementing Raspberry Pi firmware, ROM, or Linux bootloader configuration
- claiming full SD-card slot handoff, partition switching, or power-loss resilience
- introducing UART hardware validation into this change
- replacing the existing interactive SSH launch path for operator debugging

## Decisions

### 1. Use a system-level systemd service that runs the installed release as the target user

The autostart slice will install a governed systemd unit under `/etc/systemd/system/` and run the installed release as `operator`. This avoids depending on `loginctl enable-linger` and keeps boot-time startup tied to the normal target boot path.

Alternatives considered:

- `systemd --user` service with linger: rejected because it introduces extra user-manager state and a second activation dependency while `sudo -n` is already available.
- shell startup files or cron `@reboot`: rejected because they are less observable and less consistent than systemd for restart/status/journal behavior.

### 2. Reuse the installed release launcher and make the runtime explicitly headless under service management

The service will continue to launch the installed `current/launch/run_stack.sh` flow so it reuses the governed release layout, companion simulator startup, and runtime-root conventions. The OBC runtime will gain an explicit headless mode rather than trying to infer behavior from closed stdin.

Alternatives considered:

- relying on `/dev/null` stdin without code changes: rejected because the current runtime loop can exit when stdin reaches EOF.
- writing a completely separate service-only launcher tree: rejected because it would duplicate the installed release flow that packaging already established.

### 3. Keep the service bound to the `current` release pointer

The systemd unit will point at `$OBC_HOME/obc-deploy/current/launch/run_stack.sh` rather than a versioned release directory. This keeps autostart aligned with the governed install-root abstraction and lets future release promotion continue to use the `current` symlink as the active selection point.

Alternatives considered:

- pinning the unit to a specific release directory: rejected because every install would then require rewriting the unit even when the logical active release changed only through the symlink.

### 4. Provide repo-local helper scripts for install, status, and reboot probes

The repository will include helper scripts that render and install the systemd unit, show service/journal status, and perform an end-to-end reboot probe. This keeps service management reviewable and avoids ad hoc target commands drifting outside the governed workflow.

Alternatives considered:

- documenting raw `systemctl` commands only: rejected because it would make repeatable evidence capture harder and less uniform.

## Risks / Trade-offs

- [Service installation writes to `/etc/systemd/system/`] -> Keep the unit file small, deterministic, and generated by a repo-local helper; run the workload as the non-root target user.
- [A service-managed process can hide interactive debugging affordances] -> Keep the existing interactive SSH launcher intact and add a separate headless path instead of removing the REPL workflow.
- [Autostart evidence can be mistaken for full boot-chain validation] -> State explicitly in docs and evidence that this slice verifies service-managed startup after OS reboot, not firmware or partition-level boot handoff.
- [The `current` symlink can change while a service instance is already running] -> Treat release promotion and service restart as separate governed operations; document that a restart is required to switch the already-running process to a new release.

## Migration Plan

1. Add a headless runtime flag and service-aware installed launcher behavior.
2. Add a systemd unit template plus repo-local install/status/probe helpers.
3. Install and enable the service on the Raspberry Pi against the existing install root.
4. Reboot the target and verify the service relaunches the installed `current` release.
5. Record evidence, validate the change, and archive it.

## Open Questions

- Whether a later change should restart the autostart service automatically after every bundle install.
- Whether a later boot/update slice should coordinate service restart timing with formal slot promotion semantics.
